# Instagram Bot Live Visuals Design

## Objective

Make the Instagram Direct experience feel live and human to both the customer
and the manager, while preserving the existing provider and CRM truth. The
first release prioritizes two visible regressions:

1. `mark_seen` and `typing_on` must remain visible long enough to be perceived
   before the bot sends its answer.
2. A newly active conversation must appear in the manager inbox immediately and
   move to the top with a calm, spatially understandable transition.

The order/TTN lifecycle, compact statistics, and the rest of the visual audit
remain later slices. They must not be bundled into the first release because
they have separate data and responsive risks.

## Root Cause Evidence

The current worker already calls `send_sender_action(..., "mark_seen")` and
`send_sender_action(..., "typing_on")` before generation. Production was checked
read-only: the active transport is `instagram_login`, `ai_enabled=True`, the
bot is replying, and a real ephemeral `typing_on` action returned HTTP 200.
The action result is currently discarded and the next provider send follows as
soon as generation and business guards finish. Therefore the reliable failure
is not endpoint availability; it is that a very short action window is easy for
the customer client to miss, and provider failures are invisible to operators.

The manager inbox API already returns `last_message_at` and orders clients by
`-last_message_at`. The open conversation API already supports incremental
`after_id` polling. The missing piece is a lightweight list refresh and a
stable DOM reorder animation; no new database field or websocket is required
for this first slice.

## Design Decisions

### Customer typing state

- Send `mark_seen` once, then `typing_on` before AI/fallback generation.
- Keep the action helper provider-aware and return a typed success/failure
  result. Store only bounded event metadata (`action`, HTTP class, transport),
  never customer text, tokens, or raw provider payloads.
- Enforce a small minimum visible typing window for successful automated
  replies. The delay is based on reply length and capped so it cannot create a
  long queue stall. If generation itself took longer than the target, no extra
  delay is added.
- Refresh typing at a bounded interval only while generation is still running;
  do not create an unbounded background thread. Stop the indicator immediately
  before the final Send API call, and keep the existing receipt/idempotency
  boundary unchanged.
- If `mark_seen` or `typing_on` fails, the reply still follows the existing
  delivery path. The failure is visible in the operational log, not to the
  customer as an error.
- There is no sound effect. Audio would add noise and cannot be relied on in
  Instagram clients; the visible state is sufficient.

### Manager inbox live reorder

- Poll the existing clients endpoint only while the Bot tab is visible, with a
  modest adaptive interval and request cancellation for stale responses.
- Preserve the selected conversation. If the selected conversation changes,
  update its open transcript through the existing `after_id` endpoint; do not
  forcibly open another customer while the manager is reading.
- When a non-selected conversation receives a newer `last_message_at`, update
  that row in place, then move it to the top using a FLIP transition. The row
  gets one short `is-live-updated` highlight and an unread/new marker; the
  entire list does not flash.
- Reconcile by client id and preserve the current page/search/filter. If the
  incoming row no longer belongs to the active filter, remove it with a short
  exit transition. If a new row enters the current filter, insert it at the top
  with the same FLIP treatment.
- Keep the server's ordering as authoritative. The browser never invents a
  timestamp or business state.
- Respect `prefers-reduced-motion`; in that mode the list still reorders and
  marks the row, but without movement animation.

## Data Flow

```text
Instagram webhook -> durable inbound row -> worker
  -> mark_seen/typing_on -> generate reply -> bounded visible typing window
  -> typing_off -> existing Send API receipt -> durable model message

Manager browser -> existing clients API poll
  -> compare client_id + last_message_at
  -> reconcile DOM by id -> FLIP move/highlight
  -> selected conversation uses existing after_id poll
```

## Testing and Acceptance

- RED tests prove sender-action result handling, minimum-window calculation, and
  no unnecessary sleep when generation already consumed the window.
- Existing provider URL/transport tests remain green; no real customer text or
  Meta advertising events are generated by tests.
- UI contract tests prove list polling is visible-tab-only, selected client is
  preserved, stale responses cannot overwrite newer state, and the reduced
  motion class is present.
- Browser QA covers 320, 375, 768, and 1440 px: no horizontal overflow, stable
  row heights, smooth reorder, filter/search preservation, and a live open chat.
- Production verification proves the deployed SHA, daemon heartbeat, sender
  action observations, and a real manager browser session. No synthetic
  customer message is sent during verification.

## Explicitly Deferred

- Full SSE infrastructure, command palette, sound, generic payment countdowns,
  invented shipment history, and large chart-library adoption.
- Order/TTN lifecycle and compact statistics are separate commits after this
  live interaction slice is stable.
- Accessibility work is treated as QA and semantic correctness, not as a
  standalone visual feature.

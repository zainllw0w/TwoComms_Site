# Э-Б — Извинение только тому, кто ждёт; квота на пару (ключ, модель)

**Статус 2026-08-29 — реализовано локально.** Production-наблюдение владельца
29.08: клиент (обычный пользователь, не тестер) сделал репост истории и отметил
бренд. Раньше бот благодарил и разбирал изображение. В этот раз он ответил
**«Вибачте за технічну затримку. Я відновлюю деталі й невдовзі відповім вам
тут.»** — на ход, где никто ответа не ждал.

Владелец описал проблему шире, и это правильная формулировка: техническое
извинение уместно только тогда, когда человек **долго ждёт** и, возможно, уже
переспросил. В остальных случаях это спам, который выглядит как поломка. Лучше
ответить хорошо через две минуты, чем плохо через десять секунд.

## Часть 1 (ЭБ.1). Почему извинение вообще было отправлено

Драбина деградации L0…L6 из `ЭА` описана верно, и её рівень L1 говорит именно то,
что нужно: «пока бюджет хода не исчерпан — клиент видит индикатор набора, а не
текст». Оказалось, что **L1 недостижим**.

### Дефект 1: аргумент, который никто не передавал

`holding_decision()` принимает `budget_remaining_ms: int = 0` и проверяет:

```python
if budget_remaining_ms and int(budget_remaining_ms) > 0:
    return HoldingDecision(DEFER, "budget_not_exhausted")
```

Живой ход вызывал её так (`instagram_bot.py`, до правки):

```python
outage_gate = ig_provider_incidents.holding_decision(
    row, logical_turn_id=logical_turn_id
)
```

Аргумент не передавался **никогда**. Значение по умолчанию `0` делает условие
всегда ложным, то есть проверка была недостижимым кодом. Любой сбой генерации,
классифицированный как провайдерский, проходил сразу к L4 «холдинг» — через 5–10
секунд после сообщения клиента. Это и есть главная причина спама: не логика
дедупликации (она работала), а то, что решение о **времени** никогда не
принималось.

### Дефект 2: «нужен ли ответ» определялось не тем вопросом

Роль «нужен ли этому ходу ответ» играла `is_low_intent_turn()`. Она отвечает на
другой вопрос — «пустая ли реплика» (ack, эмодзи, реакция). Для репоста истории
она сработала так:

1. репост приходит вложением без текста → `reaction_or_sticker = True`;
2. но перед этим бот задавал вопрос → сработало исключение `_bot_asked_question`,
   написанное для «Добре» после «Який розмір?»;
3. исключение снимало gate целиком → ход стал «требующим ответа» → техтекст.

Репост — не ответ на вопрос бота. И, что важнее, **никто не делает репост, а
потом смотрит в Direct в ожидании квитанции**.

### Дефект 3: одиночный сбой считался поводом для извинения

```python
incident = incident or active_incident(role="chat", now=now)
if incident is None:
    ...
    return HoldingDecision(SEND, "no_open_incident")
```

Ветка читается так: «подтверждённой деградации провайдера нет, значит это
отдельный сбой хода — разрешаем один holding». Это перевёрнутая логика. Одиночный
сбой — случай, когда молчать надо **больше** всего: следующая попытка или курсор
восстановления почти наверняка ответят через 20–40 секунд. Извинение сейчас плюс
ответ через полминуты хуже, чем просто ответ через полминуты.

### Дефект 4: восстановленный ответ извинялся всегда

`_generate_recovery_draft()` выбирал между двумя turn-note по одному признаку:
«было ли уже доставлено извинение». Пока holding уходил почти всегда, это
работало. После того как holding перестал уходить, условие стало давать извинение
почти в каждом восстановленном ответе — то есть спам просто переехал на 20 секунд
позже.

## Что сделано (ЭБ.1)

**Новое понятие `ig_reply_expectation`** — одно место, отвечающее на вопрос «ждёт
ли клиент ответа». Три разных признака, которые раньше были одним:

| признак | смысл | репост истории | реакция 👍 | «Скільки коштує?» |
|---|---|---|---|---|
| `waiting` | обязывает ответить сейчас | нет | нет | да |
| `substantive_reply_owed` | должны ответить, пусть и позже | **да** | нет | да |
| `actively_waiting` | уже переспросил | — | — | если писал повторно |

Асимметрия цены ошибки задана осознанно: лишнее молчание не стоит ничего, потому
что путь восстановления доставит настоящий ответ и **без** извинения. Лишнее
извинение — ровно тот спам, из-за которого блок и появился. Поэтому по умолчанию
молчим.

**Четыре условия должны выполниться вместе**, иначе техтекста нет:

1. `expectation.waiting` — клиент действительно ждёт;
2. `budget_remaining_ms <= 0` — заявленный бюджет хода уже истрачен. Считается от
   метки провайдера на сообщении клиента, а не от начала нашей работы: если ряд
   пролежал в очереди (restart демона, stale requeue), клиент ждал реально долго;
3. открытый инцидент **или** `actively_waiting` — то есть мы прогнозируем долгую
   паузу, а не один неудачный вызов;
4. бюджет извинений (эпизод, дневной потолок) не истрачен.

**Порог времени выведен, а не назначен**: `customer_notice_threshold_seconds()` =
сумма фаз, которые клиент проводит в ожидании ответа (склейка + генерация). Пока
жив индикатор набора (`_TypingPulse`), молчание читается как «нам пишут».
Независимая константа здесь разошлась бы с реальным дедлайном при первой же
правке — та же ошибка, из-за которой окно живости демона было меньше бюджета хода.

**Репост истории получает благодарность без модели (рівень L3).**
`safe_ugc_acknowledgement()` уже приводит ответ к социальному, некоммерческому
виду и для любого решения оценки возвращает непустой текст. Значит благодарность
за отметку **не требует Gemini вообще**. Теперь провайдерский сбой на репосте даёт
клиенту именно благодарность, а не техтекст, — то есть ровно то поведение, которое
владелец помнит как правильное.

**Восстановленный ответ извиняется по тому же правилу**, что и holding: только
если клиент ждал дольше объявленного бюджета и действительно ждал. UGC-ход не
извиняется никогда.

## Часть 2 (ЭБ.2). Почему сбой вообще случился при шести ключах

### Находка: квота free-tier принадлежит паре (проект, модель)

`is_key_level_429()` трактовал 429 на free-модели как «исчерпана квота ПРОЕКТА» и
ставил в кулдаун **ключ целиком**:

```python
# 429 на free-моделі = вичерпана денна квота проекту → кулдаун усього КЛЮЧА
```

У Google лимиты free tier объявлены **на модель в проекте** (у каждой модели своя
строка RPM/RPD). Следствие прежнего поведения: 429 по дневному лимиту самой
дефицитной модели (3.7-flash) закрывал ключ вместе с 3.6, 3.5 и lite, у которых
лимит в разы больше. Шесть ключей исчерпывались за день по худшей модели, и живой
ответ оставался без ключа — при полном отсутствии нагрузки. Это и объясняет
«6 ключей, а всё равно извинения».

Сделано: кулдаун получает **пара (ключ, модель)** (`GeminiKeyState.model_cooldowns`).
Кулдаун всего ключа остаётся для `topup` — там закончились деньги проекта, и это
действительно про все модели сразу. Вызов без `model` сохраняет прежнее поведение,
поэтому внешний код и старые тесты не меняются.

### Находка: hedging лечит латентность, а не квоту

Волна из ЭА/Э-HEDGE запускает все ключи лучшей модели со ступенчатым стартом
1.5 с. Под квотой это вредно: 429 приходит за ~0.3 с, следующий ключ волны
стартует через 1.5 с и получает тот же отказ. Один ход остужает несколько ключей,
и следующий клиент начинает с меньшим пулом — «улучшение» ухудшало доступность.

Сделано: волна открывается только если по этой модели нет остывших пар
(`model_quota_pressure`). Под давлением идём последовательно: первый 429 закрывает
пару и мы честно спускаемся по лестнице, не потратив на разоблачение три
параллельных запроса.

### Находка: фон и чат сталкивались на первом же заимствованном ключе

Пулы были такими: чат own `[API, API2]`, borrow `[API3…API6]`; management own
`[API3, API4]`. То есть первый ключ, который берёт чат после своих двух, —
собственный ключ фона. Владелец предложил развести направления, и это правильно.

Сделано: фоновые роли идут **навстречу** чату, от последнего ключа к первому
(`own [API6, API5]`, `borrow [API4, API3]`). Встреча происходит в середине пула и
только под реальным давлением.

## Чего сознательно НЕ сделано

- **Отдельная «интеллектуальная подсистема», решающая, извиняться ли.** Решение
  нужно принять по четырём булевым признакам за миллисекунды на пути, который и
  так упирается в провайдера. Ещё один вызов модели здесь означал бы ещё одну
  причину задержки. Интеллект здесь — это правильный предикат, а не LLM.
- **Опрос остатка квоты у провайдера.** Дешёвой конечной точки нет, а проверка
  тратит ту самую квоту, которую измеряет. Учимся на реальных отказах.
- **Перевод пути ответа на async.** Узкое место — ожидание HTTP-ответа
  провайдера, демон и так многопоточный. Async ORM Django 6.1 здесь не помогает.
- **Смена классификации «наш дедлайн» → не провайдерский сбой.** Проверено:
  инциденты регистрируются в слое пула по точным классам отказа
  (`gemini_keys.py`), а не по этой грубой метке, поэтому фиктивных инцидентов она
  не создаёт. После новых условий (ожидание + бюджет + инцидент/переспрос)
  дедлайн сам по себе техтекста не даёт. Менять classify без нужды — риск без
  выигрыша.

## Открытый вопрос к владельцу (нужен ответ)

`GEMINI_KEY_PROJECT_GROUPS` не задан ни в `settings.py`, ни в `.env.example`.
Пул поэтому считает все шесть ключей независимыми квотными идентичностями. Если
несколько ключей созданы **внутри одного** Google-проекта (обычный путь в AI
Studio: «create API key» несколько раз), то квота у них общая, и 429 на одном
мгновенно повторится на его «братьях» — лестница выгорает за секунды.

Что нужно: сказать, в скольких разных Google Cloud проектах живут шесть ключей.
Если в разных — задать соответствие в `GEMINI_KEY_PROJECT_GROUPS` не требуется, но
полезно для наблюдаемости. Если в одном — код должен знать об этом, иначе он
переоценивает пул в шесть раз.

## Тесты

- `tests_ig_reply_expectation.py` — 18 тестов: репост никогда не получает
  техтекст (в том числе после вопроса бота — тот самый путь), реакция после
  вопроса бота не должна ничего, короткий ответ на вопрос бота по-прежнему ждёт
  ответа, фото без текста — это запрос, свежий ход видит индикатор набора,
  одиночный сбой молчит, переспросивший клиент получает одно сообщение, открытый
  инцидент даёт ровно один holding, флаг откатывает поведение.
- `tests_gemini_keys.py::PerModelQuotaCooldownTests` — 6 тестов: дневная квота
  одной модели не закрывает остальные модели ключа, минутная истекает для пары,
  `topup` закрывает ключ целиком, вызов без модели сохраняет прежнее поведение,
  истёкшие пары не накапливаются в строке, лестница продолжается на том же ключе.
- `tests_checker_gemini.py::ChatHedgeDisciplineTests` — волна не открывается под
  квотным давлением и открывается на здоровом пуле.
- Переписаны с объяснением причины: 5 тестов восстановления (извинение теперь
  реакция на долгое ожидание), `test_free_model_429_cools_the_pair_key_model_not_the_whole_key`
  (прежняя формулировка утверждала неверную семантику квоты), два теста порядка
  пула.

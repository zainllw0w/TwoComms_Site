# Э-HEDGE — Все ключи лучшей модели, а не два

**Статус 2026-08-29 — закрыто.** Production-наблюдение владельца 28.08.

## Что было

Клиент спросил про футболки с Харьковом. Телеметрия хода:

```
GEMINI_API2 / gemini-3.7-flash  read_timeout  17.4s  candidate_index=1
GEMINI_API  / gemini-3.7-flash  read_timeout  10.4s  candidate_index=2
GEMINI_API2 / gemini-3.6-flash  succeeded     10.4s  candidate_index=7
```

Индексов 3–6 **не существует**: четыре ключа на лучшей модели не пробовались вообще.
Клиент получил ответ более слабой моделью, хотя четыре ключа 3.7 даже не спросили.

## Две причины

**1. `CHAT_PRIMARY_ATTEMPT_LIMIT = 2`.** После двух «медленных» попыток цикл
выходил на следующую модель в цепочке.

**2. Арифметика последовательного бюджета.** При дедлайне 35 с:

| попытка | бюджет вызова | израсходовано |
|---|---|---|
| 1 на 3.7 | 16.5 с | 16.5 с |
| 2 на 3.7 | 8.2 с | 28.9 с |
| — | — | на fallback осталось 6.1 с |

Две последовательные попытки съедали 83% дедлайна. Даже без лимита третья
получила бы 4 с, четвёртая — меньше двух. Последовательный перебор шести ключей
при таких таймаутах физически не укладывается в бюджет живого ответа.

**Ключевое наблюдение.** `read_timeout` пришёл на **оба** ключа — значит медленной
была сама модель, а не ключи. Но узнать это можно было только опросив остальные,
чего система не делала.

## Решение: hedged requests со ступенчатым старом

`management/services/gemini_hedge.py`

Первый ключ стартует сразу. Если через `HEDGE_STAGGER_SECONDS` (1.5 с) ответа нет —
стартует второй, и так далее, максимум `MAX_IN_FLIGHT = 3` одновременно. Первый
успех возвращается немедленно, остальная волна гасится.

**Расход квоты в нормальном режиме не растёт.** Если первый ключ отвечает за 2.4 с
(типичное значение из телеметрии), второй не стартует вообще — `stop.wait(delay)`
возвращает True до истечения задержки.

Арифметика для 6 ключей, stagger 1.5 с, read timeout 12 с:

| ключ | старт | крайнее завершение |
|---|---|---|
| 1 | 0.0 с | 12.0 с |
| 2 | 1.5 с | 13.5 с |
| 3 | 3.0 с | 15.0 с |
| 4 | 4.5 с | 16.5 с |
| 5 | 6.0 с | 18.0 с |
| 6 | 7.5 с | 19.5 с |

Все шесть исчерпаны к 19.5 с, на fallback остаётся 15.5 с. Против 28.9 с на две
попытки и 6.1 с на fallback раньше.

### Ожидание первого успеха, а не всей волны

`stop.wait()` вместо `future.result()` по каждому: если один ключ висит все 12 с,
а другой ответил за 2 с, клиент получает ответ за 2 с. Иначе hedged-вызов
вырождался бы в самого медленного кандидата и смысла не имел.

Отставшие вызовы не блокируют возврат: `pool.shutdown(wait=False)`, их HTTP
доживает сам. В телеметрию они пишутся как `abandoned_after_winner` /
`abandoned_unfinished` — это **не** отказ, и скорборд не считает их провалом.

### Адаптивный stagger

Если скорборд знает, что ключ обычно отвечает за 2 с, следующий ждёт 2.5 с
(`ADAPTIVE_STAGGER_FACTOR = 1.25`), а не фиксированные 1.5 с. Чем стабильнее ключ,
тем меньше хеджирования.

### Терминальный отказ гасит волну

404 «модель не существует для этого проекта» или 403 не изменятся от другого
ключа. `aborts_wave` гасит волну сразу — продолжать значило бы жечь квоту на
заранее известный результат.

## Скорборд: знание вместо проверок

`management/services/gemini_scoreboard.py`

**Ни одного тестового запроса к провайдеру.** Каждый реальный ход клиента уже
пишет факт в `GeminiRequestAttempt` (Э0.1). Скорборд читает эти факты и отвечает
на один вопрос: в каком порядке пробовать кандидатов сейчас.

- окно 20 минут: достаточно, чтобы увидеть quota-окно 429, и достаточно мало,
  чтобы вчерашний сбой не влиял на сегодняшний порядок;
- снимок кешируется на 8 с: при 20–30 одновременных клиентах это один SQL-запрос
  на всех, а не проверка на каждого;
- нет данных → базовый порядок пула, никакой деградации.

### `read_timeout` больше не понижает ключ

Разделены два класса:

- `_MODEL_SLOWNESS_KINDS` (`read_timeout`, `http_408`, `http_5xx`, `transport`) —
  медленная **модель**, ключ живой;
- `_KEY_FAULT_KINDS` (`quota_429`, `invalid_key`, `permission_denied`) — проблема
  именно ключа.

Раньше таймаут уводил ключ в хвост очереди, хотя следующий раз он ответил бы
мгновенно. Ключ с `quota_429` теперь стоит **ниже** ключа с таймаутом.

Ни один кандидат не выбрасывается: задача — быстрее найти отвечающего, а не
решить за провайдера, кто сломан.

## Побочная находка: аудио-анализ не мог получить свой timeout

```
KEY_LEASE_SECONDS = 70
GEMINI_TIMEOUT = (10, 90)     # сумма 100 с
allowance = min(100, 70 - 1) = 69  →  фактически (6.9, 62.1)
```

Настройка выглядела действующей и не действовала. Одна константа лизинга
обслуживала и чат (бюджет хода 35–45 с), и аудио (десятки секунд).

Введена `lease_seconds_for(role)`: чат держит ключ коротко, чтобы не блокировать
его для других клиентов; `LONG_JOB_ROLES` (`management`, `checker`) получают
120 с. Тест `test_audio_management_keeps_long_timeout` падал **до** этих правок —
это был незамеченный баг, а не регрессия.

## Переписанные тесты

Два теста фиксировали дефектное поведение:

- `test_slow_transients_degrade_after_at_most_two_primary_calls` → 
  `test_slow_transients_try_every_key_before_degrading_the_model`. Само название
  содержало проблему: он требовал уйти на слабую модель после двух таймаутов.
- `test_ordinary_incident_recovers_within_35_seconds` проверял свойства
  последовательного перебора (ровно две попытки, каждый следующий timeout меньше).
  Оба были следствием деления бюджета последовательно. Теперь проверяется то, что
  действительно должно быть истиной: все ключи опробованы, fallback получил резерв,
  ни один вызов не просит больше бюджета хода.

В обоих случаях в docstring записано, почему старое ожидание было неверным.

## Тесты

22 новых в `tests_gemini_hedged_pool`:

- быстрый первый ключ не запускает второй (расход квоты не растёт);
- медленный первый ключ отдаёт победу другому, и волна не ждёт его до конца;
- все шесть ключей опробованы, когда каждый падает;
- терминальный отказ модели гасит волну;
- исчерпанный дедлайн пропускает остальных;
- `read_timeout` не понижает ключ ниже `quota_429`;
- скорборд не делает ни одного вызова к провайдеру;
- ни один кандидат не выбрасывается из очереди;
- `not_attempted` строки игнорируются;
- снимок кешируется между вызовами.

Полный прогон `management`: **50 падений против 53 базовых**, новых нет.
Исправлено три: `test_audio_management_keeps_long_timeout` и два MariaDB-теста,
которые перестали падать после разделения лизинга.

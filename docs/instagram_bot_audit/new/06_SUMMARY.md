# Резюме аудита Instagram-бота TwoComms

**Дата завершения:** 2025-01-25  
**Версия кодовой базы:** `origin/main` на момент аудита  
**Объём проверенного кода:** ~12 700 строк `instagram_bot.py` + связанные модели, миграции, тесты

---

## Главный вывод

Бот имеет **развитую техническую инфраструктуру** — почти всё, что нужно для работы, уже написано. Основные проблемы **не в отсутствии возможностей, а в порядке их применения и в деталях политики**.

Три критических находки (P0):

1. **Недоверенный текст клиента попадает в инструкции модели** (`NEW-PROMPT-001`) — прямая уязвимость для prompt injection;
2. **Lifecycle-сообщения не доходят из-за closed window** (`NEW-CRIT-001`) — написанный post-purchase контур не работает;
3. **`hidden_at` не проверяется** (`NEW-TECH-001`) — удалённый клиентом диалог продолжает получать сообщения.

Все три **исправляемы** без переписывания архитектуры.

## Ключевые решения, принятые в плане

### 1. Один реестр узлов воронки вместо двух

**Отклонено:** раздельные реестры для обязательного и контекстного.  
**Принято:** одно `FunnelNodeDefinition` с полями политики, различающими lifecycle, blocking, evidence, retention.  
**Обоснование:** семь различий между типами узлов выражаются семью полями; два реестра создают проблему синхронизации и удваивают миграции.

### 2. Post-sale как отдельная проекция, не расширение `stage`

**Отклонено:** добавить `advocate`, `repeat_ready` в `IgClient.FUNNEL_ORDER`.  
**Принято:** отдельная проекция с узлами `feedback_requested`, `ugc_offered`, `follow_asked`, `repeat_ready`, связанная с `order_id` и `episode_id`.  
**Обоснование:** post-sale и продажный эпизод имеют разную жизнь; расширение одного enum ломает аналитику и делает регресс непонятным.

### 3. Карточки не генерируются моделью

**Принято:** payload, URL, суммы — из детерминированного кода и authoritative источников. Модель выбирает карточку из разрешённого набора, но не формирует её содержимое.  
**Обоснование:** модель может выдумать цену, ссылку, срок. Карточка — это действие с последствиями; её содержимое должно быть проверяемым.

### 4. Память как проекция анализа, не параллельный вызов

**Отклонено:** два независимых вызова Gemini для памяти и анализа.  
**Принято:** анализ создаёт структурированные факты с evidence; память рендерит их по релевантности.  
**Обоснование:** два вызова дают два возможных ответа об одном диалоге; они могут противоречить и попадут в промпт одновременно.

### 5. Shadow + holdout для продажных решений

**Принято:** каждое изменение next-best-action, оффера, fast-track проходит shadow-режим, затем выкат на малую когорту с holdout и явными условиями остановки.  
**Обоснование:** нельзя экспериментировать на всей базе без возможности отката; нельзя измерять только конверсию без возвратов, жалоб, takeover.

### 6. Детерминированный контекст-планировщик до retrieval

**Принято:** intent определяет набор блоков детерминированно (правила + фингерпринт); retrieval — только для редких сложных случаев и как отдельный этап.  
**Обоснование:** tool call = второй round-trip = дополнительная задержка; при SLA 35/45 секунд это ощутимо; непрозрачный retrieval скрывает, почему блок попал в промпт.

### 7. Opt-in как gate для post-purchase, не универсальная блокировка

**Принято:** opt-in открывает сообщения за пределами 24-часового окна; внутри окна — транзакционные правила.  
**Обоснование:** Meta API даёт 24 часа на транзакционное; opt-in расширяет на post-delivery и follow-up; универсальная блокировка до opt-in закрывает продажи.

## Риски, если не исправлять

### Бизнес-риски

1. **Незабранные посылки** — прямой убыток: обратная доставка + замороженный товар + потеря повторной продажи. Для COD — ещё и потеря выручки;
2. **Потеря LTV** — весь post-purchase контур написан, но не работает из-за closed window;
3. **Навязчивость без измерения** — конверсия может расти при росте навязчивости, а долгосрочный ущерб проявится позже;
4. **Переобещание** — «уточню і вернусь» без resolver создаёт необеспеченное обещание; клиент ждёт, и это худший вид потери.

### Технические риски

1. **Prompt injection** — недоверенный текст в инструкциях позволяет клиенту переопределить поведение;
2. **Burst → несколько ответов** — горячий клиент получит несколько параллельных попыток закрыть сделку;
3. **Голодание живого ответа** — фоновая работа может занять все соединения; клиент ждёт;
4. **Устаревшие действия после исправления** — клиент сказал «не L, а M», а follow-up по L всё ещё в очереди.

### Операционные риски

1. **Алерты обесцениваются** — непонятные сообщения приходят часто, их перестают читать, настоящая проблема проходит незамеченной;
2. **Нет метрики пути клиента** — heartbeat и зелёная карточка не доказывают, что клиент получил корректный исход;
3. **Отсутствие отката** — изменение продажного решения без shadow-режима и holdout = эксперимент на всей базе без возможности вернуться.

## Оценка объёма работ

**Общее число чекбоксов:** 367 шагов в 72 подэтапах 9 этапов.

**Порядок величины по этапам:**

- **Э0** (фундамент) — 7 шагов, ~2–3 недели. Ничего не меняет для клиента, но обязателен для остального;
- **Э1** (opt-in и карточки) — 12 шагов, ~3–4 недели. Открывает post-purchase;
- **Э2** (доставка) — 11 шагов, ~2 недели. Много мелких исправлений границ;
- **Э3** (истина данных) — 18 шагов, ~4 недели. Самый трудоёмкий этап, много проверок;
- **Э4** (воронка) — 9 шагов, ~3 недели. Видимость для менеджера и агента;
- **Э5** (память) — 6 шагов, ~2 недели. Адресность и проекция;
- **Э6** (post-purchase) — 6 шагов, ~2 недели. Открывается после Э1;
- **Э7** (контракты агента) — 8 шагов, ~3 недели. Усиление интеллекта;
- **Э8** (операции) — 7 шагов, ~2 недели. Устойчивость;
- **Э9** (остаточное) — 5 пачек, ~1 неделя. Мелкие правки.

**Реалистичная оценка:** 6–9 месяцев при одном разработчике полный день с учётом тестирования, выката, мониторинга результатов и исправления обнаруженного по ходу.

**Критический путь:** Э0 → Э1.0–Э1.4 → Э3.7 → Э1.5 → Э4.1 → остальное Э4 → Э5 → Э6.

## Метрики успеха

### Главная метрика (Э0.7)

**Доля клиентов, получивших корректный финальный исход** по трём путям:

1. Продажный ответ → `inbound сохранён → решение → разрешённая отправка / блокировка политикой / человеческий кейс → receipt провайдера / unknown`;
2. Срочная поддержка / передача → аналогично;
3. Lifecycle-событие клиента → аналогично.

**Текущее состояние:** неизвестно (метрика не собирается).  
**Целевое:** >95% для путей 1 и 2; >80% для пути 3 (post-delivery сложнее).

### Вторая по важности (Э6.1, Э6.2)

**Доля post-delivery сообщений, дошедших до клиента.**  
**Текущее состояние:** близко к 0% (blocked by window, требование оплаты для доставки).  
**Целевое:** >70%.

### Другие ключевые метрики

- **Число ходов до ссылки** (Э4.5) — текущее неизвестно, цель: <3 для горячего клиента;
- **Доля незабранных посылок** (Э6.2) — прямо в деньгах;
- **Доля ответов на запрос фидбека** (Э6.3) — определяет, работает ли LTV-контур;
- **P95 latency живого ответа** (Э8.1) — не должна вырасти при добавлении контрактов;
- **Prompt tokens per intent** (Э5.2, Э5.4) — должны упасть при адресной памяти.

## Что уже работает хорошо

1. **Durable inbound** — провайдерские повторы не создают дублей ответа;
2. **Анализ с evidence** — структурированные факты с message ID и confidence;
3. **Discount approval gate** — канонический SHA, authenticated callback, revalidation;
4. **Размерная сетка из каталога** — `checkout_readiness()` корректно выводит `not_applicable`;
5. **Guardrails для post-sale сервиса** — подавление продажи работает;
6. **Ad attribution** — `ad_id` используется в промпте для адаптации тона;
7. **Многопоточный демон** — архитектура правильная, нужны только границы бюджета.

## Главные риски плана

1. **Объём.** 367 чекбоксов — это много. Риск выгорания или потери фокуса. **Митигация:** этапы независимы; можно выбрать подмножество по приоритету владельца;
2. **Отсутствие данных.** Несколько этапов начинаются с MEASURE, потому что без цифр приоритет угадывается. Если измерение покажет, что проблемы нет, этап можно пропустить;
3. **Изменения кода upstream.** План привязан к `origin/main` на момент аудита. Если основная ветка ушла вперёд, часть находок может устареть. **Митигация:** `03_FINDINGS_RECONCILIATION.md` показывает, как проверять актуальность;
4. **Opt-in может быть недоступен.** Э1.0 проверяет это первым делом. Если недоступен, весь Э6 откладывается до решения канала доставки;
5. **Сопротивление карточкам.** Если администратор считает карточки «не своими», вся ветвь Э1 теряет смысл. **Митигация:** показать одну карточку в shadow-режиме и измерить конверсию против текста.

## Следующие шаги

1. **Проверить актуальность.** Запустить чеки из `03_FINDINGS_RECONCILIATION.md` на текущем `origin/main`. Если основная ветвь ушла вперёд, часть находок может быть уже исправлена;
2. **Выбрать подмножество по приоритету владельца.** Не обязательно делать все 367 чекбоксов; можно начать с P0 + P1 и остановиться, когда метрики достигнут цели;
3. **Исправить P0 немедленно** (Э3.1, Э3.18, Э6.1 — три правки, все простые);
4. **Запустить Э0.3** (воронка причин lifecycle) — это MEASURE, который определит, насколько серьёзна проблема post-delivery и стоит ли вообще делать Э6;
5. **Проверить Э1.0** (доступность opt-in) — если недоступен, нужно решение канала до начала Э6;
6. **Начать с Э0** (фундамент проверяемости) — без него нельзя доказать ни одну правку.

## Часть 0. Блокирующее противоречие, найденное до проектирования

Заказчик просит: через ~25 минут после выдачи ссылки, если оплаты нет, бот пишет
«у вас закінчилось посилання, ви не оплатили, чи актуально?».

**Сейчас это технически недоказуемо:**

1. У платёжной ссылки **нет TTL**. В payload Monobank не передаётся ни `validity`,
   ни `expire` (`bot_payments.py:54-63`). Срок жизни целиком на стороне банка,
   в коде не задан и не отслеживается, поля `invoice_expires_at` в `IgDeal` нет.
2. Статус `expired` попадает в систему только через `poll_deal_status`
   (`bot_payments.py:537`), который вызывается из `poll_pending_deals` —
   а её cron **удалён и мёртв с 8 июля** (F-OPS-001).
3. Текущий follow-up через 45 минут утверждает **прямо противоположное** —
   «посилання на оплату ще активне» (`bot_followups.py:276-280`) — и делает это,
   ни разу не проверив факт.

Значит порядок работ обратный запросу: сначала сделать истечение **наблюдаемым**,
и только потом строить на нём каскад. Иначе бот будет уверенно говорить
«ссылка активна», когда она мёртвая, и наоборот — а хуже всего написать
«ваша ссылка истекла» человеку, который только что заплатил.

## Часть 1. Три структурных дефекта, из-за которых добивки почти нет

Это находки уровня «функция написана, но не работает». Все проверены лично.

### 1.1 Финальный офер 10% недостижим в проде (P0)

`Kind.FINAL` создаётся только при `explicit_negotiation=True`
(`bot_followups.py:181-183`). Единственный продакшн-вызов —
`schedule_rescue_offer(client, now=now)` (`:554`) — **без этого флага**.
`explicit_negotiation=True` встречается только в тестах
(`tests_ig_sales_automation.py:403,406`).

Механика отказа: после отправки 5% ставится `discount_offered_percent=5`,
а `next_discount_percent` (`:177-186`) при `current=5` проходит так:
`current >= 10`? нет → `explicit_negotiation`? нет → `current <= 0`? нет → **`return 0`**.

Следствие: ветка `pct == 10` в `compose_followup` (`:288-297`) — мёртвый код,
финальный офер не отправлялся ни разу.

### 1.2 Ветка платёжной добивки мертва (P0)

`schedule_after_bot_reply` проверяет `deal.status == AWAITING_PAYMENT` (`:238-239`),
но единственный продакшн-вызов передаёт только `client`, `reply`, `control`
(`instagram_bot.py:5342-5346`) — **без `deal=`**.

Поэтому планирование платёжного напоминания держится исключительно на
`client.stage == PAYMENT_PENDING` (`:240`), которую ставит `bot_orders.py:1038`
внутри `try/except: pass`. Если `set_stage` упал или стадию откатил классификатор,
клиент со свежей платёжной ссылкой попадает в ветку `QUALIFICATION` (2 ч)
и получает «чи актуальне ще замовлення?» вместо напоминания об оплате.

### 1.3 Окно Meta системно убивает половину 12-часовых задач (P0)

`meta_window_deadline = last_message_at + 23ч` (`:56-60`),
quiet hours = 10:00–19:00 (`:28-29`).

Разбор: клиент пишет в 09:00 → deadline 08:00 следующего дня.
`thinking`-задача = now+12ч = 21:00 → `next_allowed_send_at` видит `>= 19:00`
и переносит на **10:00 следующего дня** → `due > deadline` → задача создаётся
сразу со `status=SKIPPED`, `kind=MANAGER_TASK`, `skip_reason=meta_window_closed`
(`:146-150`).

Она не `pending`, её никто не выполняет, а в UI для `meta_window_closed`
**даже нет метки** (`bot.html:800-803` знает только `meta_window`) — отображается
сырым кодом. Все диалоги, где клиент последний раз писал между ~00:00 и ~11:00,
теряют «подумаю»-добивку молча. Это примерно половина суток.

**Вывод:** реальная длина каскада сегодня — **1–2 сообщения**, а не 4.
`FOLLOWUP_MAX_ATTEMPTS = 4` (`:31`) — это счётчик ретраев ошибки отправки
(`:493-510`), а не количество касаний клиента.

### 1.4 После оплаты добивка структурно невозможна (P0)

`_client_allows_followup` возвращает `already_converted` при подтверждённой оплате
(`:112-118`). Логично для продаж — и катастрофично для фулфилмента: клиент
оплатил, но не дал ПІБ/місто/відділення → **добить его нельзя**. Деньги приняты,
заказ лежит. `collect_np_and_fulfill` (`bot_orders.py:207`) вытягивает данные
только реактивно, если клиент сам что-то написал.

## Часть 2. TTL ссылки: как сделать истечение наблюдаемым

| Вариант | Плюсы | Минусы |
|---|---|---|
| **(A)** `validity` в payload + планировать задачу на `now + TTL` | детерминированно, без сетевых вызовов, момент известен до секунды, ноль нагрузки на API | это **прогноз**, а не факт: банк может отменить инвойс раньше; оплата в последнюю минуту с недоставленным webhook даст ложное «ссылка истекла» — сообщение человеку, который заплатил |
| **(B)** опрашивать статус инвойса | **факт**; один вызов закрывает оплату, истечение и отмену; защита от подделки webhook | нужен живой cron (сейчас мёртв); лаг до интервала опроса; расход квоты API |
| **(C)** оба | планирование дешёвое и точное, отправка только после подтверждения | сложнее |

**Решение: (C) с разделением ролей.**
`validity` + `invoice_expires_at` — **источник планирования** (когда просыпаться).
Поллинг — **источник истины** (можно ли это утверждать клиенту): задача при
исполнении первым делом дёргает `poll_deal_status`, и только при статусе из
`MONO_CANCELLED`/`MONO_PENDING` отправляет текст про новую ссылку.
При `success` задача гасится (`bot_payments.py:341` это уже делает).

**Почему именно так:** (A) без (B) рискует написать оплатившему «ваша ссылка
истекла» — худший исход для доверия. (B) без (A) не даёт события в нужный момент
и деградирует до «опрашиваем всё каждые 4 минуты».

**TTL = 24 часа**, задача — на **T+23 ч** (до истечения, а не после). Обоснование:
- TTL должен быть ≈ окну Meta (23 ч). Если ссылка живёт дольше окна, возникает
  зона «ссылка活 жива, а написать клиенту нельзя» — недостижимая для добивки.
- 24 ч читается как «до завтра» и даёт легитимный повод для касания
  («лінк закінчується сьогодні») — дедлайн без давления.
- Короткий TTL (1–3 ч) даёт частые мёртвые ссылки и лишние перевыпуски;
  длинный (7 дней) убивает срочность и множит расхождение «сток продан,
  а ссылка жива» — резерва стока в чекауте нет (F-PAY-002).
- Для перевыпущенной ссылки — 12 ч: второй заход с подтверждённым интересом.

**Важно:** `create_payment_link` идемпотентно переиспользует инвойс (`:31-37`) —
нужен guard «reused только если `invoice_expires_at > now + запас`»,
иначе клиент получит мёртвую ссылку.

## Часть 3. Каскад добивки: 9 сценариев с текстами

Общие правила: счёт касаний ведётся **на сценарий** (`level` + `reason` уже есть);
любое входящее клиента обнуляет шаг и передаёт ход реактивному ответу;
после ответа бота каскад входит заново с сохранённым счётчиком.

**Глобальный терминал:** `opt_out`, `explicit_no_buy`, `spam_abuse`, `hidden_at`,
`manager_takeover`, подтверждённая оплата, закрытое окно Meta,
суммарно ≥5 автоматических касаний за 30 дней. После терминала —
`stage=COLD`, `primary_objection=NO_REPLY`, запись `lost_reason`.

### (а) Ссылка выдана, оплаты нет — 5 касаний за 72 ч

**A1 — T+25 мин** (условие: `poll_deal_status` ≠ success, ссылка жива)
```
Нагадаю про оплату — посилання ще активне 💛
Якщо щось не відкривається, не проходить оплата або хочете інший спосіб —
просто напишіть, я поруч і швиденько розберемось.
```

**A2 — T+4 ч** (не оплачено, клиент не писал)
```
Бачу, оплата ще не пройшла. Підкажіть, будь ласка, є якесь питання, що зупиняє?
Найчастіше це розмір, доставка або спосіб оплати — з будь-яким із цього
допоможу за пару хвилин. Товар поки тримаю за вами.
```

**A3 — T+23 ч, до истечения** (`invoice_expires_at - now < 1ч`)
```
Посилання на оплату діє ще близько години, потім автоматично закриється.
Якщо плануєте оформити — краще зробити це сьогодні. Якщо потрібен новий лінк
або хочете змінити розмір/кількість — напишіть, зроблю нове посилання без проблем.
```

**A4 — событие «ссылка истекла», подтверждённое опросом**
```
Посилання на оплату вже неактивне — воно живе добу, тому автоматично закрилось.
Якщо замовлення ще актуальне, скажіть одне слово «так» — і я одразу зроблю нове.
Розмір і ціну пам'ятаю, нічого повторювати не треба.
```

**A5 — T+72 ч, финальный офер 5%** (ни одного ответа за весь каскад)
```
Останнє від мене по цьому замовленню 💛
Як для першого замовлення можу дати -5% і оформити все за вас — треба лише
підтвердження. Якщо зараз не актуально, теж окей: більше не турбую,
а коли захочете — просто напишіть, я на місці.
```

**B1 — T+2 ч**
```
Підкажіть, будь ласка, чи підходить така ціна?
Якщо є сумніви — можу показати фото на людині, розповісти про тканину
або підказати розмір по ваших параметрах. Просто напишіть, що цікавить.
```

**B2 — T+24 ч, вечерний слот**
```
Ще раз привіт 👋 Не хочу губити ваше замовлення.
Модель, яку ви дивились, є в наявності. Якщо готові — оформлю за 2 хвилини,
потрібні лише розмір і місто. Якщо передумали — теж скажіть,

```

**B3 — T+72 ч, 5%**
```
Фінальна пропозиція від мене: -5% на це замовлення, якщо оформимо сьогодні.
Далі не турбуватиму. Захочете повернутись — просто напишіть, все підкажу 💛
```

### (в) «Подумаю» — 3 касания за 7 дней

**C1 — T+20 ч, вечерний слот** (не 12 ч: 12 ч почти всегда попадает в quiet
либо за окно Meta — см. 1.3)
```
Не тисну, просто нагадаю про себе 🙂
Якщо залишилось питання — по розміру, тканині чи доставці — відповім коротко
і по факту. А якщо потрібно більше часу, скажіть, і я нагадаю пізніше.
```

**C2 — T+72 ч, с 5%**
```
Ваше замовлення ще можна оформити — розмір, який ви дивились, у наявності.
Як бонус за очікування можу дати -5%. Якщо цікаво — напишіть «так»,
решту зроблю сам.
```

**C3 — T+7 дней, закрывающее**
```
Останнє повідомлення від мене по цій моделі 💛
Якщо колись захочете повернутись — просто напишіть, я все пам'ятаю
і оформлю швидко. Гарного дня!
```
После C3 — обязательно `lost_reason="thinking_exhausted"`, иначе каскад
перезапустится при следующем ответе бота.

### (г) «Дорого» после отработки — 2 касания за 96 ч

Ключевое: ценовое возражение требует **изменения условия**, а не напоминания.
Сейчас идёт по тому же пути, что «подумаю» (`:248-251`), что неверно.

**D1 — T+24 ч, сразу 5%**
```
Подумав над вашим питанням по ціні.
Можу зробити -5% на це замовлення — це максимум, що доступно без узгодження.
Плюс доставка Новою Поштою за тарифом перевізника, без нашої націнки.
Якщо так підходить — оформлю зараз.
```

**D2 — T+96 ч, 10% финал** (требует, чтобы 10% стал достижим — см. 1.1)
```
Фінальний варіант, узгодив окремо: -10% на це замовлення.
Це справді останнє, що можу запропонувати. Якщо не підходить — все ок,
більше не нагадую і не буду відволікати 💛
```

### (е) Нет нужного размера — реакция + событие, без тайм-каскада

Напоминать «размера нет» бессмысленно, поэтому здесь событийная логика.

**F1 — сразу, в реактивном ответе**
```
На жаль, саме цього розміру зараз немає в наявності.
Два варіанти: можу підібрати схожу модель, де ваш розмір є, або поставлю вас
у чергу — і напишу першому, щойно розмір з'явиться. Що зручніше?
```

**F2 — событие «размер появился»** (обязательна проверка окна Meta;
если закрыто — задача менеджеру, автоотправка недопустима)
```
Хороша новина 💛 Розмір, який ви чекали, знову в наявності.
Модель та сама, ціна не змінилась. Якщо ще актуально — оформлю зараз, поки є.
```

**F3 — T+14 дней без restock**
```
Ваш розмір поки не завезли — не хочу тримати вас у невідомості.
Можу показати схожі моделі, де розмір є зараз. Або залишаю вас у черзі
й напишу, коли з'явиться. Як зручніше?
```

Сейчас планируется одно, а второе (5% rescue) не создаётся, потому что

## Часть 4. Quiet hours: реактивный ответ против инициации

**Различает ли код сейчас?** Да, но случайно: `next_allowed_send_at` применяется
только внутри `bot_followups` (`:141`, `:456`, `:500`), а реактивный путь
`process_pending → send_text` окна не проверяет вообще. Требование заказчика
(«ночью отвечать можно, инициировать нельзя») формально выполняется,
но нигде не выражено как правило.

**Проблема окна 10:00–19:00:**
1. Отрезает вечерний прайм-тайм Instagram (19:00–22:00) — самое конверсионное время.
2. Конфликтует с окном Meta: 9 разрешённых часов против 23 → задержки ≥12 ч
   массово умирают (см. 1.3).
3. Асимметрия: задача, созданная в 19:01, ждёт почти сутки.

**Предлагаемое правило:**

| Тип | Окно | Обоснование |
|---|---|---|
| Реактивный ответ | 24/7 | клиент инициировал; молчание ночью хуже ответа ночью |
| Проактивная инициация | 10:00–21:30 Kyiv | захватывает вечерний прайм, не пишет ночью |
| Аварийное окно ради окна Meta | 09:00–22:30 | только если иначе задача теряет право на отправку |
| Ночь 22:30–09:00 | запрещено всегда | без исключений |

**Что делать с задачей, попавшей в quiet hours** — три случая вместо одного:
1. Сдвиг укладывается в окно Meta с запасом ≥1 ч → сдвинуть на ближайший слот,
   целясь в вечер (19:00–20:30), если он ближе, чем утро.
2. Сдвиг выводит за окно Meta, но аварийное окно позволяет → отправить в нём.
   Потерять контакт хуже, чем написать в 22:15.
3. Даже аварийное не спасает → `MANAGER_TASK` со `status=PENDING`
   (не `SKIPPED`, как сейчас) + текст-заготовка + пометка «окно истекает в HH:MM».
   Сейчас такая задача создаётся уже мёртвой и не видна как работа.

Плюс: планировать не «сейчас + задержка», а **целиться в слот** для задач
с горизонтом ≥20 ч. И вынести quiet hours в настройки — сейчас в кодовой базе
**две несогласованные конфигурации тишины**: 10:00–19:00 (`bot_followups.py:28-29`)
и 21:00–08:00 (`config_versions.py:89`, для другой подсистемы).

## Часть 5. Механизм: крон, таймеры или события

**Ответ: механизм менять не нужно, он уже правильный.** Durable `IgFollowUpTask`
с `due_at`, который дренит тикер демона (`process_due_followups` вызывается
из `_run_work_cycle`, `run_instagram_bot.py:261` и `:285`). Состояние целиком
в БД, убитый демон не теряет задачи, watchdog поднимает процесс за минуту.
Есть lease на клиента, epoch-проверки, экспоненциальный backoff.

Чистые таймеры в памяти не подходят (демон перезапускался 27 раз по логу).
Чистый cron уже показал слабость: задачу удалили и никто 24 дня не заметил.

**Что добавить:**
1. **Событийный слой:** `trigger ∈ {time, event}` + `event_key`
   (`invoice_expired:{id}`, `restock:{product}:{size}`, `ttn:{deal}`).
   Ключевой приём: задачу истечения планировать **в момент выдачи ссылки**,
   когда TTL уже известен — это снимает зависимость от опроса провайдера.
2. **Перенести `poll_pending_deals` в тикер демона** с кэш-локом (образец —
   `ig_profile_batch`, `run_instagram_bot.py:255`). Убирает класс отказа
   «cron исчез». Плюс расширить фильтр за пределы `AWAITING_PAYMENT`
   (истёкшие сделки сейчас выпадают, F-PAY-004).
3. **Двухфазный claim:** `pending → sending` в транзакции + `claimed_by` →
   отправка → `SENT`, плюс реклейм зависших. Сейчас падение процесса между
   `send_text` и записью `SENT` даёт повторную отправку после рестарта.
4. **Уникальность pending** по `(client, kind, level)` через nullable
   `pending_slot` (приём уже применён в `IgInboxRefreshRun.open_slot`).
   Сейчас дедуп процедурный, в БД индекса нет.
5. **Приоритизация:** `limit=20` с `order_by("due_at")` ставит платёжные
   напоминания в общую очередь с «чи актуально».

## Часть 6. Возражения: жизненный цикл вместо события

### 6.1 Почему сейчас нельзя ответить ни на один вопрос заказчика

| Вопрос | Можно? | Почему нет |
|---|---|---|
| Сколько возражений было | частично | считаются события-сигналы; одно возражение на 3 сообщения = 3 строки, а «подумаю» = **0 строк** |
| Каких типов | частично | пишутся только 3 типа; 9 из 12 реальных возражений невидимы |
| Сколько закрыто | **нет** | в `IgConversationSignal` нет состояния (`ig_bot_models.py:2978-2992`) |
| Каким методом закрыли | **нет** | метод отработки не существует как понятие |
| Сработал ли метод | **нет** | нет ни метода, ни связи с последующим поведением |
| Что убило сделку | **нет** | `primary_objection` перетирается на `NO_BUY` (`:788`) и обнуляется при ресете (`ig_funnel_reset.py:164`) |

**Четыре дефекта детекции, найденные при разборе:**
- **`THINKING` не создаёт сигнала вообще** (`:824-826` — только `objection`
  и `readiness`, нет `add(...)`), и типа `thinking_objection` нет в `Type`.
  Самое частое возражение в рознице не логируется.
- **`Objection.TRUST`, `DELIVERY`, `OTHER` — мёртвые choices**, не присваиваются нигде.
- **`PRICE_RE` ловит вопрос как возражение:** `ціна|скільки|сколько|price|how much`
  → обычное «скільки коштує?» становится `price_objection`. `SIZE_RE` ловит
  одиночные `s|m|l` → ответ «M» на вопрос бота становится `size_concern`.
  Поэтому 31 и 44 на проде — **смесь вопросов и возражений**, доверять нельзя.
- **Исходное возражение теряется** при потере сделки и при ресете воронки.

### 6.2 Модель: новые таблицы, не расширение сигнала

Расширять `IgConversationSignal` опасно: это append-only event log с
`get_or_create` по `(client, message, type, value)`; мутабельное состояние
сломает детерминированность `reconcile_rules_projection`, на которой держится
`dedupe_key` снапшотов. Плюс у него жёсткий FK на MyISAM-таблицу `IgClient`.

**Решение:** аддитивно расширить `Type` (безопасно) + две новые таблицы:

`IgObjection` — агрегат жизненного цикла (одна строка = одно возражение в одном
эпизоде): `client`, `episode`, `objection_type`, `state` (`open/handled/resolved/
abandoned`), `is_true_objection`, `first/last_message`, `repeat_count`,
`attempts_count`, `resolution_method`, `outcome` (`purchased/lost/silent/
manager_taken/unresolved`), `readiness_before/after`, `opened_watermark_message_id`
(защита от ресета), `dedupe_key`.

`IgObjectionAttempt` — append-only попытки: `method`, `claimed_by`, `verified`,
`verification_reason`, `reply_message`, `client_response_message`,
`result` (`accepted/re-objected/silent/escalated/purchased`).

**Переходы:**
```
(нет) --detect--> open --применён метод--> handled
handled --клиент двинулся вперёд--> resolved
handled --повторил то же возражение--> open (repeat_count += 1)
open|handled --тишина/отказ--> abandoned
```

**Связка «метод → результат» на трёх уровнях:** микро (`result` по следующему
ходу), мезо (дельта `readiness`), макро (`outcome` из `episode.state`).
Тогда «какой метод чаще закрывает возражение по цене» считается автоматически.

### 6.3 Как фиксировать метод детерминированно

**Рекомендация: тег + валидатор, без дополнительных LLM-вызовов.**

1. Модель ставит `[OBJHANDLE:price:value_breakdown]` — инфраструктура готова,
   `_CONTROL_TAG_RE` уже парсит `[NAME:value]` и режет теги до отправки.
2. Валидатор проверяет **очищенный текст** по отпечаткам метода. Например:
   `value_breakdown` — ≥2 маркера ценности (`тканин|футер|DTF|друк|шиємо|щільн`)
   **и** нет слова `знижк`; `risk_reversal_exchange` — есть `14 дн` **и** `обмін|поверн`;
   `size_consult` — запрос замеров **и** знак вопроса.
3. **Ключевой инвариант:** в `handled` переводит только `verified=True`.
   Заявленный но неподтверждённый метод оставляет возражение `open` —
   иначе метрика «закрыто» станет самообманом.
4. Тега нет вовсе → `method='none'`: честный сигнал «бот проигнорировал возражение».
5. LLM-судья — только в офлайн-контуре анализа, пакетно, не в онлайне.

### 6.5 Блок возражений в промпт (~15 строк)

```
[ЗАПЕРЕЧЕННЯ — службове, клієнт цього не бачить]
Відкриті: ціна (2-й раз, з 14:20), розмір (1-й раз).
Вже застосовано і НЕ повторювати тими ж словами:
  ціна → value_breakdown (реакція: заперечив знову)
  розмір → size_consult (реакція: без відповіді)
Закриті: передоплата → explain_prepay_purpose (клієнт погодився).
Правила:
1. Не повторюй метод, який вже не спрацював — зміни кут.
2. Спочатку перевір, чи це справжня причина: «це єдине, що зупиняє?»
3. Знижку не пропонуй — цим керує система.
4. Якщо одне заперечення повторилось 3 рази — не тисни, постав [MANAGER].
5. Коли відпрацював заперечення, додай у кінці [OBJHANDLE:тип:метод].
```

**Когда НЕ включать:** подтверждённая оплата, `intent=support` (рекламация,
а не продажа), `no_buy`/`opt_out`, `manager_takeover`, реакции-эмодзи.
**Обрезка:** максимум 3 открытых + 3 закрытых, только релевантные методы.

### 6.6 Правила продаж, которых нет в промпте

Сейчас про возражения **одна строка** (`models.py:3555-3557`), ни одной техники.
Плюс запрет на скидку без альтернативного инструмента. Не хватает:

- **истинное vs ложное возражение:** «Підкажіть, це єдине, що зупиняє?»
- **согласись → переформулируй → ответь:** никогда не начинать с «але»
- **изоляция:** «Окрім ціни, є ще щось, що стримує?»
- **проверка на завершение:** «Якщо з розміром розберемось — оформлюємо?»
- **цена без скидки:** ценность, разложение на сезон носки, дешёвая альтернатива
- **момент гарантии:** говорить об обмене именно при страхе ошибиться,
  и **не** говорить, если клиент уже готов платить — посеет сомнение
- **повторное возражение = стоп-сигнал:** дважды — сменить подход,
  трижды — прекратить продавать и поставить `[MANAGER]`

## Часть 7. Статистика точек падения

### 7.1 Почему сейчас нельзя посчитать

1. **`stage` — перезаписываемое поле, а не история.** `bot_stats_api` группирует
   именно его (`bot_views.py:3908-3914`). `new=150` означает «150 сейчас имеют
   метку new», а не «150 не дошли до квалификации».
2. **Две последние стадии физически не пишутся:** `ORDER_CREATED` и `DONE`
   выводятся на лету из эпизода (`_operational_client_stage`, `:2647-2655`),
   а статистика читает сырое поле. Шаги «заказ создан» и «получен» недостижимы.
3. **5 путей записи стадии не оставляют события** (см. F-STATE-004),
   самая болезненная дыра — `ig_checkout.py:633`: переход в `CHECKOUT`
   («клиент пошёл платить») не оставляет следа вообще.
4. **Событие слишком бедное:** нет `occurred_at` отдельно от `created_at`
   (бэкфилл ломает временную ось), нет `event_key`, нет `actor`, нет `episode`.
   Прецедент есть рядом: B2B-аналог `ClientStageEvent` (`models.py:2879-2909`)
   имеет всё это.
5. **Ключевые шаги стадию не меняют:** «названа цена», «предложена скидка»,
   «отработано возражение», «ссылка открыта», «замолчал» — не переходы.
6. **Период считается по `last_message_at`** (`:3882-3891`): клиент, написавший
   месяц назад и ответивший сегодня, целиком попадает в «сегодня».
   Сумма по дням ≠ итог за месяц.
7. **Отвал не существует как факт:** `Objection.NO_REPLY` объявлен и
   **никогда не присваивается**; `signal NO_REPLY` объявлен и **без producer'а**.

### 7.2 Воронка переходов

Единица наблюдения — **эпизод**, не клиент (иначе математика повторных покупок
неверна). `entered(N)` / `advanced(N)` / `CR(N)=advanced/entered`.

Переходы: написал→ответил бот; ответил→товар; товар→цена; цена→ссылка;
ссылка→оплата; оплата→заказ; заказ→ТТН; ТТН→получен.
Плюс: назвал размер; возражение→снято; скидка→куплено; замолчал→вернулся.

### 7.3 Отвал как событие

Модель `IgFunnelDropOff` (append-only): `kind` (`silence|explicit_refusal|opt_out|
unreachable|spam|superseded`), `reason_code`, `stage_at_drop`, `objection_at_drop`,
`silence_hours`, `followups_sent_before`, `detected_by`, `is_recoverable`,
`recovered_at`, `recovered_by_followup`.

**Критично разделить:** `unreachable` (наша вина — Meta заблокировала доставку)
от `silence` (поведение клиента). Смешивать = скрывать техдолг под видом
плохой конверсии.

**Три уровня:** `pending_silence` (порог не пройден) → `drop_off(recoverable)`
(добивка легитимна) → `churned` (только тут `state=LOST`).

Пороги тишины — **в рабочих часах**, иначе ночь и выходные дадут ложные отвалы:
`new/qualifying` 24 ч, `product_matched` 24, `checkout` 12, `payment_pending` 6,
`lead_manager` 4.

### 7.4 Что показывать администратору

9 блоков, каждый с явным вопросом «какое решение принять»:

1. **«Где падает»** — воронка 8 шагов: `вошли · перешли (CR%) · в процессе ·
   отвалились`, шаг с максимальной потерей подсвечен. → куда вкладывать неделю.
2. **«Почему падает на шаге X»** — причины отвала, безвозвратные отдельно
   от восстановимых. → если сверху `silence_after_paylink`, проблема в оплате,
   а не в скриптах.
3. **«Летальность возражений»** — `встретилось · дошло до оплаты · летальность %`.
   → какой блок скриптов переписывать первым. Абсолют не годится: «дорого»
   частотнее, но летальность может быть ниже, чем у «передоплата».
4. **«Эффективность добивания»** — по `(kind, level)`: `отправлено→ответили→купили`
   + контрольная строка «без follow-up». → где остановить цепочку.
5. **«Скидки»** — `предложено · купили · недополученная маржа` + купившие без
   скидки. → не покупаем ли конверсию, которая была бы и так.
6. **«Бот против менеджера»** — три плитки. Считается из `creation_mode` **уже сегодня**.
7. **«Время на шаге»** — median и p90 с отсечкой порога тишины. → где follow-up
   приходит слишком поздно.
8. **«Требует действия сейчас»** — эпизоды с открытым восстановимым отвалом,
   сортировка по `сумма × вероятность`. → единственный блок, конвертирующий
   статистику в деньги напрямую.
9. **«Реклама»** — существующая таблица + честное предупреждение
   «атрибуция не собирается: 289/289 без ad_id».

**Правила периодов:** cohort вместо snapshot; резать по `occurred_at`,
никогда по `created_at` (инбокс-рефреш массово пишет старые сообщения сегодняшним
временем) и никогда по `last_message_at`; незавершённый день — три числа
на шаг (`перешли/отвалились/ещё в процессе`), иначе сегодняшний CR всегда
выглядит катастрофой; при `entered < 20` показывать «мало данных» вместо процента
(на 289 клиентах половина разрезов ниже порога).

### 7.5 Событийная модель

Единая таблица `IgFunnelStepEvent` (append-only) с 16 типами событий:
`conversation_started`, `bot_replied_first`, `product_pinned`, `variant_selected`,
`price_quoted`, `paylink_issued`, `paylink_viewed`, `objection_raised`,
`objection_handled`, `discount_offered`, `manager_engaged`, `order_created`,
`ttn_created`, `delivered`, `drop_off`, `recovered`.

**Правило для producer'ов:** писать **в той же транзакции**, что и мутация
состояния. Отдельный `try/except: pass` (как в `set_stage`) воспроизведёт
текущую неполноту.

**Бэкфилл возможен** для `paylink_issued`, `order_created`, `ttn_created`,
`delivered`, `payment_confirmed`. **Невозможен** для `price_quoted`,
`objection_handled`, `discount_offered`, `drop_off` — история начнётся с деплоя,
и это надо показать в UI честно.

## Часть 8. Контекст-бюджет: когда подавать инструкции

### 8.1 Фактический размер

| Блок | Максимум | Всегда? |
|---|---:|---|
| `system_prompt` | 3 136 | да |
| оперативные директивы (`knowledge_base`) | **без лимита** | условно |
| база знаний бренда | cap 24 000 (факт 3 788) | условно |
| каталог | cap 16 000 / 250 позиций | условно |
| playbook-инструкции | **без лимита** | условно |
| `PAYMENT_PROTOCOL_NOTE` | 1 079 | **да** |
| `ANTI_HALLUCINATION_NOTE` | 334 | **да** |
| `SALES_AUTOMATION_GUARDRAILS` | 812 | **да** |
| память | 4 022 | условно |
| контекст клиента | ~1 600 | условно |
| история (вне system) | до 12 000 | да |

**Код-максимум ≈ 56 000 символов** (≈22–28k токенов). Типичный «привіт»
при пустом `knowledge_base` ≈ 26 000. Вход в 3–6 раз больше выхода
(`maxOutputTokens: 4096`) на **каждое** сообщение.

Плюс: динамические блоки стоят **в конце**, что ломает даже неявное
префиксное кэширование.

### 8.2 Почему это бьёт по качеству, а не только по стоимости

Доказательства в самом коде — заплатки, которые появились именно из-за размывания
внимания модели:
- **Две редакции протокола оплаты** на расстоянии ~20k символов
  (`models.py:3583-3588` без `[ITEM]` и `instagram_bot.py:480-499` с `[ITEM]`)
  → появился ворот на битые item-теги `paylink_item_gate` (`:586-595`).
- **Каталог как 65 однотипных строк задаёт режим «перечисляй»** → промпт
  **дважды** запрещает списки (`models.py:3546`, `:3560-3563`).
- **~200 чисел в контексте** (id рядом с ценами) → ворот `payment_link_allowed`.
- `PAYLINK_PHRASES` как фолбэк «если модель забыла тег» (`:250-258`),
  `_strip_invented_pay_urls` (модель писала свои платёжные URL),
  `ANTI_HALLUCINATION_NOTE` с прямой ссылкой на реальный инцидент
  («як це сталось із реальним товаром «Харків Edition»»).

### 8.3 Бюджет по стадиям

Ключевые решения матрицы:
- На `new` база знаний и полный каталог не влияют ни на один токен решения —
  нужен только сужающий вопрос. Каталог → только индекс (D0).
- `PAYMENT_PROTOCOL_NOTE` до появления товара **сам себя запрещает**
  («Якщо товар ще не визначено — тег не став»), значит 1 079 символов — шум.
  Подавать с `checkout`.
- На `paid` и позже наличие протокола оплаты — **приглашение выставить второй счёт**.
- **На постпродажной стадии sales-правила должны быть выключены.**

**Механизм «скидка клиенту с обменом» найден точно:** «хочу обміняти» ловится
`SUPPORT_RE` → `intent=support`, но `tags_for_client` **безусловно** добавляет
`{"global","core","sales"}` (`bot_playbooks.py:11`), а `SALES_AUTOMATION_GUARDRAILS`
с текстом про rescue-оферы инжектится **всегда** (`:3669`).
Выключать надо на обоих уровнях: не подавать sales-текст и не добавлять тег `sales`.

### 8.4 Каталог: три уровня
- **D0 индекс (всегда, ~1.5–2.8k):** категории с количеством и диапазоном цен +
  полный список `id — назва` (~40 симв/позиция вместо ~200).
- **D1 выборка (qualifying, 8–12 строк):** отбор по словам сообщения + intent.
- **D2 карточка (от product_matched):** выбранный товар + цвета с остатками
  + **размеры** через `resolve_product_sizes` + до 3 аналогов.

Против «модель не видит товар»: полный индекс имён всегда + явная семантика
обрезки («Відсутність товару в цьому зрізі НЕ означає, що його немає») +
fail-loud вместо `except: pass`.

### 8.5 Единая иерархия истины (замена трём «высшим приоритетам»)

1. системные факты (оплата/заказ/ТТН/TTL) → 2. служебные протоколы →
3. оперативные директивы админа → 4. каталог → 5. договорённости текущего диалога →
6. база знаний бренда → 7. память-резюме (**никогда** не источник цифр).

После ввода — убрать «найвищий пріоритет» из оперативных директив,
«вища за історичну пам'ять» из коммерческой истины и заплатку про UA/RU.

### 8.6 Что добавить (компактно, ~1 800 символов вместо десятков тысяч)

`[СТАН КЛІЄНТА]` (стадия/язык/готовность/товар) — все стадии;
`[СИГНАЛИ ДІАЛОГУ]` — данные есть, в промпт не идут;
`[ВІДКРИТЕ ЗАПЕРЕЧЕННЯ]` — qualifying…payment_pending;
`[РОЗМІРИ ТОВАРУ]` — от product_matched;
`[ПОСТПРОДАЖНИЙ РЕЖИМ]` — заменяет sales-правила на paid+;
`[ПОСИЛАННЯ НА ОПЛАТУ]` с TTL — payment_pending.

**Ориентир:** «привіт» с ~26 000 до ~6–8k; `payment_pending` до ~10–12k;
постпродажный диалог до ~5k без продающих правил.
